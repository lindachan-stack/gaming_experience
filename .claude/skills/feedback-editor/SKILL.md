# 處理 review feedback 的流程

以資深工程師的角度處理，把模糊的意見還原成真正要解決的問題。

feedback 的字面內容通常不是要做的事。「這段看不懂」可能是命名爛、可能是缺註解、
也可能是邏輯真的錯了。先判斷意圖，再動手。

## 1. 先讀，不要先改

- 讀完**全部** feedback 再開始，不要逐條即刻修改。
- 讀被指涉的原始程式碼／文件，確認註解指的是哪一行。
- 找出彼此衝突或重複的意見，這些一定要問，不能自己選一邊。

## 2. 分類每一則意見

| 類型 | 判斷方式 | 處理 |
|---|---|---|
| 明確指令 | 說了要改什麼、改成什麼 | 直接改 |
| 症狀描述 | 只說了哪裡不對／看不懂 | 找根本原因後改，不是加註解掩蓋 |
| 提問 | 在問「為什麼這樣寫」 | 回答；只有確認是問題才改 |
| 意圖不明 | 無法判斷想解決什麼 | **停下來問使用者**，不要猜 |

## 3. 動手前先列清單

改之前先輸出一份對照表，讓使用者能核對：

```
- feedback #n（檔案:行）→ 判定的真正問題 → 打算怎麼改
```

有任何一項落在「意圖不明」，先問完再開始。

## 4. 改寫原則

- 只改 feedback 指到的地方。不順手重構無關程式碼、不順手改格式。
- 修根本原因，不做暫時性 workaround。
- 遵循專案既有慣例（見 CLAUDE.md）；SQL 一律先讀 `.claude/agents/sql.md`。
- 文件與註解只描述「現在的規則」，不寫「原本是 X 改成 Y」這類演進過程。

## 5. 回報

逐項列出實際動過哪裡：檔案、行、改了什麼、對應哪一則 feedback。
沒改的項目要說明原因（已經正確、需要使用者決定、超出範圍）。
不要只回「已完成」。
